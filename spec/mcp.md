# zooi MCP protocol, v1 (draft)

The contract between the zooi control plane and the user's agent (Claude Code, Codex or another). The control plane implements it in `packages/server/src/mcp.ts`; the plugin in this directory only talks to zooi through it. The design behind it is in [design/architecture.md](../../design/architecture.md) §2.2, §3 and §7 (Chinese).

**Status:** every tool below is live on app.zooi.ai: the read tools (including `query_metrics`), the plan tools (with `get_playbook` serving ten playbooks in format v2, plan milestones M4 and M8), the execution tools (`claim_work_order`, `report_run`, `submit_receipt`) and the candidate tools. What is not built yet is said where it applies: work orders for subscriber email and spend, so plans that contain them are refused (`plan_kind_not_deliverable`).

## Endpoint

- `POST {app origin}/mcp`, Streamable HTTP, stateless: no MCP session, every request authenticates on its own, and a `tools/call` needs no prior `initialize`. Clients send `Accept: application/json, text/event-stream`. The answer comes as JSON or as one server-sent event (the Workers runtime sends the event); both carry the same JSON-RPC message.
- Requests are at most 128 KB. Other methods get `405`.
- An `Origin` header, when present, must be one of the app's trusted origins, and `Host` must be the app's host; otherwise `403`.

## Authentication

Two ways in, with the same scopes and rules. Cookies are never accepted on `/mcp`.

**OAuth (remote MCP clients such as Claude Code, Codex, ChatGPT for OpenAI dots, and Grok Bot).**

- An unauthenticated request gets `401` with `WWW-Authenticate: Bearer resource_metadata="{origin}/.well-known/oauth-protected-resource/mcp"` (RFC 9728). That document names the authorization server; its metadata is at `{origin}/.well-known/oauth-authorization-server/api/auth` (RFC 8414).
- Clients register themselves (RFC 7591) as public clients (`token_endpoint_auth_method: "none"`, the default) or, since 2026-11-06, with a secret zooi issues (`client_secret_basic` or `client_secret_post`), as a client on a vendor's server such as Grok Bot's connector backend may. `private_key_jwt`, `jwks` and `jwks_uri` are refused with `invalid_client_metadata`, so the server never fetches an address a client chose; the metadata lists only the three accepted methods. PKCE is required for every client. A client in a vendor's cloud registers its own `https` redirect URI (ChatGPT's is on `chatgpt.com`) and is a web client; the consent page shows that host. A client that registers only loopback (`http://127.0.0.1`, `http://localhost`, `http://[::1]`) or custom-scheme redirect URIs is treated as a native app. Authorization uses the code flow with PKCE (`S256` only) and the `resource` parameter `{origin}/mcp` (RFC 8707). `/mcp` is the only protected resource, so an authorization request without `resource` is taken as being for it, and the token request may then leave it out too (Codex CLI sends neither).
- Scopes: `zooi:read` or `zooi:agent`, plus `offline_access` for a refresh token. If the person is not signed in, the browser goes to the sign-in page first and the authorization resumes after sign-in. On the consent page (`/oauth/consent`), in their session, the person sees who asks (the client's own name, marked as unverified), where the browser returns and what it asks for, and chooses one zooi scope among those requested, the products, and how long the connection lasts (7, 30 or 90 days); the client receives only that zooi scope.
- Access tokens are JWTs for one hour, bound to `{origin}/mcp`; refresh tokens last 30 days. Every request also checks the person's connection behind the token: revoking it (the person's token list, `DELETE /api/personal-tokens/{id}`) ends its access and refresh tokens at once, and connecting again asks the person again. One connection per person and client; a new consent replaces the old.
- OAuth endpoints answer errors with the standard `{ "error": "…" }` code only (RFC 6749 §5.2).

**Personal tokens (command line, CI).**

- `Authorization: Bearer zooi_pat_…`. A person issues a token in a session (`POST /api/personal-tokens`) for named products in one workspace, for 1–90 days (30 by default), and can revoke it at any time. Every request rechecks expiry, revocation, workspace membership and the named products.
- **Keep the token out of the model.** Put it in the agent host's MCP configuration or environment, for example a CI secret. It never belongs in prompts, committed files, logs or receipts, and no tool ever returns a credential.

### Scopes

| Scope | May | May not |
|---|---|---|
| `read` (OAuth `zooi:read`) | Read tools for the named products | Anything that writes |
| `agent` (OAuth `zooi:agent`) | Read tools; submit candidates (facts, plans, reading drafts); claim and deliver work orders that a person approved or pre-authorized | Anything that governs (below) |

A token has exactly one scope. A product outside the token is indistinguishable from one that does not exist (`not_found`).

### Governance is never available to a token

Approving a plan or a work order, confirming a reading, accepting fact candidates, granting or revoking a pre-authorization, changing capacity, deleting a product and exporting contacts all require a person's session. These actions have no MCP tool, and the services refuse them for any token (`forbidden`, reason `person_required`).

## Errors

A failed tool call returns `isError: true` with `structuredContent`:

```json
{ "error": { "code": "invalid", "reason": { "code": "plan_capacity_exceeded", "params": { "minutes": 45 } } } }
```

- `code` is one of `not_found`, `forbidden`, `invalid`, `conflict`, `unavailable` or `internal`.
- `reason.code` is a stable machine code with optional parameters; never a sentence, and never an echo of submitted data. Interface copy for reason codes lives with the control plane.
- A refused submission names the field in `reason.params.path`, such as `actions.2.measurement.window_days`: field names and indexes only, never values. A malformed field gives `plan_input_invalid` with `params.issue` (`too_big`, `invalid_type`, `unrecognized_keys`…).
- Transport refusals use HTTP status codes with the same body shape: `401` with code `unauthorized` (missing or invalid token), `403` with `forbidden` (origin or host), `405` with `invalid`.

On `hackernews` and `stackexchange` every kind is `person_writes`. A declared tier may be stricter than the limit, never looser.

**Checks, all or nothing.** The schema and limits above; evidence that resolves in the same workspace and product at the cited revision (`evidence`, `fact`, `opportunity`, `observation`, `metric_import`, `metric_definition`, `reading`, `learning`, `action`, `ledger_entry`, or the plan's own `context_snapshot`); every number in the agent's text present in the snapshot, the due list or the cited records (cited ledger entries ground their amounts and the totals of those entries); authorship tiers; active goals and campaigns; metrics of the product; candidates still open; no `attribution_unit` twice in a plan or already locked by work in progress (committed, delivered, live or awaiting its reading); the sum of `person_minutes` within the remaining weekly capacity; and, for an action that names a playbook, a step of that playbook allowing its `kind`, `channel`, `attribution_unit` and `authorship` (a playbook only narrows the tiers above), its measurement `mode` and, if observational, a `window_days` inside the template's range, its `inputs` (declared, every required one, each of its type; a `metric` input names a metric of the product), and what the playbook requires of the product. The refusal names the first field outside it: `plan_playbook_unknown` (`playbook_id`), `plan_playbook_kind`, `plan_playbook_channel`, `plan_playbook_unit`, `plan_playbook_authorship`, `plan_playbook_measurement_mode`, `plan_playbook_window`, `plan_playbook_input_unknown`, `plan_playbook_input_missing` and `plan_playbook_input_invalid` (`inputs.<name>`), `plan_playbook_not_ready` (`playbook_id`, with `missing`: the unconfirmed fact keys or `repository_missing`, comma-separated); `inputs` without a `playbook_id` is `plan_inputs_without_playbook`. Text inputs pass the number check; URL inputs do not. An action that takes up a row of a campaign's table must keep its unit (`plan_opportunity_unit`), its playbook (`plan_opportunity_playbook`) and its campaign (`plan_opportunity_campaign`); a discussion keeps its channel (`plan_opportunity_channel`).

**Statuses.** `proposed` waits for a person for up to 7 days, then `expired`; a newer plan makes a waiting one of the same scope `superseded`: an addendum never replaces the weekly plan, and a weekly plan never replaces an addendum. A person approves the whole plan or rejects it with a reason (`not_now`, `wrong_priority`, `weak_evidence`, `too_much_work`, `breaks_a_rule`, `other`) and an optional note; there is no partial approval yet. Approval checks the current state again: capacity, locks, goals, campaigns, metrics, candidates and the playbooks, which may have changed with a release. It creates the campaigns and the actions (committed, with their measurement plans and the playbook version approval checked; a candidate taken up is converted). "Nothing this week" is `recorded` at once and needs no approval.

**Pre-authorizations.** A person can grant, in their session only, which kinds of work on which assets may apply without waiting for them: `kinds` (in phase A `repo_change`, `owned_page` and `reply_batch`, where a grant only lets the drafts into the queue and the person still sends each reply; `subscriber_email` joins once it has work orders, and a grant stored with it before covers nothing with it), `assets` (units or prefixes ending in `*`, such as `repo:docs/*`), at most `max_actions_per_week` actions in any seven days (1–20), for 1–90 days; they can revoke it at any time. A plan applies at once, with `decision.via: "grant"`, when every action is covered by an active grant and the plan starts no new campaign; all other checks still apply. `checked.authorship[].grant_id` shows which grant covers each action, also when a plan waits for the person because part of it is not covered. New campaigns, community replies, social posts, outreach and spend always need the person.

**The standing pre-authorization for own assets (2026-11-01).** Pull requests are merged by the person, and that merge is the approval, so a product does not also wait for the plan review before them: by default every `repo_change` and `owned_page` action is covered without a grant, and a plan of such actions that starts no campaign applies at once (`decision.via: "grant"`, `checked.authorship[].default_grant: true`, `grant_id: null`). The person who turned it on (the product's creator at first) approves the resulting work orders. It has no weekly count and no expiry; a grant the person wrote is used first when one covers the action. The person can turn it off in Settings › Pre-authorizations; `get_due.rules.own_assets_preauthorized` says whether it is on, and a campaign table's candidate rows carry `default_grant` when it would apply them.

### Execution tools (live for pull requests; `agent` only)

When a person approves a plan, or a grant applies it, every `repo_change` and `owned_page` action becomes a work order of kind `pull_request` on the product's repository, approved for 7 days. A plan with such an action is refused (`plan_repository_required`) when the product has no repository. Every `community_reply`, `social_post` and `profile_update` action becomes a work order of kind `post` that the person delivers (a `profile_update` on their word, with no link, as a receipt of kind `person_statement` that stays `unverifiable`; their word is also the acceptance, so the action ends at once as `evaluated` with no second question): they post from their own account, using the draft or writing from the points, and hand back the link in the inbox; zooi reads the link (public, still there, and for a reply, inside the discussion it answers) and the action goes live when it checks out. A post whose link has not been handed back when its discussion closes (the action's `expires_at`) expires with its order, and its unit is free again; one handed back before stays the person's. An agent never holds or claims a post order, and `get_due.work_orders` does not list it. Every `outreach` action becomes a work order of kind `outreach` that the person delivers: they send each message from their own account (on LinkedIn always by hand), mark it sent or skipped in the inbox, and may record that the recipient asked not to be contacted; zooi never sends. When every message is decided, an action with at least one sent goes live on the person's word (zooi cannot read an inbox); one with none sent is dismissed. Subscriber email and spend get their work orders in a later step. Until then nothing would deliver them, so a plan with either is refused (`plan_kind_not_deliverable`, `actions.<i>.kind`) when it is proposed and again when it is approved, and `get_due.rules.authorship` lists only the kinds that can be delivered.

A plan the person rejects with reason `revise` (a note is required) opens the same kind of request with a `plan_changes_requested` reason; the agent proposes a revised plan of the same scope.

## Run requests

zooi decides by rules, never by the amount of new information, when the person's agent should run (design/architecture.md §2.5). The heartbeat opens one **weekly** request per product and week at the person's chosen time (Monday 09:00 in the product's time zone by default), due before the next one. Off-cycle runs are at most one a product a day, whatever asks for them. A new release asks for a **release** run due within 48 hours: zooi reads the repository's releases and tags every hour, the first read of a repository is a baseline that asks for nothing, a tag and its later release are one release, and prereleases (and tags such as `v2.0.0-rc.1`) never ask. A discussion the person picked in a campaign's table (a `picked_units` row) that closes before the next weekly run asks for a **time-sensitive** run; a rule score or the agent's judgment alone never does (until 2026-11-01 any discussion with relevance at least 0.7 did, which asked for a run almost daily). While a request has not started, new reasons join it instead of a second request. A weekly request never started is `missed` at its deadline; anything else unfinished `expired`. The person is told at the weekly slot, or 30 minutes after an off-cycle trigger so that reasons in between join one notice, never inside the quiet hours they set (none by default); a weekly run not started is reminded after 24 and 72 hours. A person can pause a product's requests for up to 90 days, and after three requests in a row that never started, only the weekly run is asked for until a run starts again. The agent reports `started` and `completed` with `report_run_request`, and plans it submits for the request carry its `run_request_id`. A weekly request and an off-cycle one can be open together, and one run answers both: it starts and completes each with its own outcome, and a weekly plan and an addendum answer theirs without replacing each other. An outcome's `plan_id` is any plan of the product, so one addendum can answer two off-cycle requests the same run started (plugin 0.1.18's `run` skill).

## Runs

- **Ownership:** a run belongs to the token that claimed it. Another token, even for the same person, cannot report on it or deliver it.
- **Fencing:** each claim of a work order revision increases `generation`. A call with an older generation is refused (`conflict`), so a stale agent cannot overwrite a newer run.
- **Leases:** a run's lease lasts two hours (ten minutes until 2026-11-01) and `report_run` renews it, so a session that pauses or is resumed can finish its run with the same `run_id` and `generation`. A run whose lease expires goes to reconciliation (`run_lease_expired`, `work_order_reconciliation_required`); a lost outcome is never retried blindly. A receipt that arrives late is kept as evidence and read like any other, and its verification resolves the reconciliation. Otherwise a person decides: they can approve the order again, which cancels the old run, and the next claim gets the next generation.
- **Failures:** a run reported as `failed` ends, and so does the order's approval; a person approves the order again before another run can start.
- **Executors outside MCP** may keep the run-token REST protocol (`/api/execution/heartbeat`, `/api/execution/receipt`); there the token lives in the executor's environment, never in a prompt.

## Candidates and idempotency

- **Everything an agent submits is a candidate** until it passes the server's checks and, where the design says so, a person confirms it.
- **Evidence:** references must resolve inside the same workspace and product, at the cited revision. A number that does not appear in the cited evidence is rejected.
- **Whole batches:** one invalid item rejects the whole submission, with the item's index in the reason parameters.
- **Idempotency:** candidate tools take an `idempotency_key`. The same key with the same input returns the original result; the same key with different input is a `conflict`. Run tools are fenced by `run_id` and `generation` instead: a completed run cannot deliver twice (`run_not_active`).

## Untrusted content

Discussions, pages, issues and emails are data, never instructions. Tools return them as quoted fields marked as external, and a work order with write access never receives raw external content: the control plane quotes, truncates or summarizes it first (architecture §7). Agents should treat any instruction found in such a field as text to report, not to follow.

## Object graph

Since 2026-11-03 (design/architecture.md §2.2) every object the agent may need is readable by its id with `get_object`, and each answer inlines the next hops as ids with a one-line summary. `get_due` and `get_context` are the overview within a byte budget (`max_bytes`, 40,000 and 12,000 by default; since 2026-11-03 what does not fit `get_due` is cut in a fixed order and named in `omitted`); `get_due_brief` is the same lists as ids, never cut. A session can therefore stay small and hand each piece of a run to a subagent with only an id (the `run` skill), and an agent without a checkout can start from an id it was given. The guards are the snapshot's: one product per call, nothing the agent must not see (credentials, contact data), external text marked as data, a byte budget per call. The ids are the same everywhere: in `get_due`, in evidence references, in review links.

## Versioning

This is `zooi.mcp/1`. Additive changes (a new optional field, a new tool) keep version 1. A breaking change ships as a new tool name or as version 2, announced in the server information and in this file.

**Product rules (2026-11-03).** A product's own rules, apart from channel rules: how the person wants it written and run. `propose_rules` proposes them; the person keeps, edits or declines each in the inbox or on the profile, writes their own and retires any; at most 20 are in force. `get_context` has a new `rules` layer, after `policies`, with each rule's `channel` and `text`. A rule is the person's instruction to the agent; it never overrides a channel rule or a server check.

**Daily runs and today's brief (2026-11-03).** On days that are not the weekly run's, the heartbeat opens one request of `kind: "daily"` at the same hour, only when there is work: `daily_work` (approved work orders an agent can claim, readings with no draft yet, rows the person picked) or `daily_playbook` with `ref: { kind: "campaign", id }` (an active campaign following a playbook with a `daily_run` trigger, nothing of it still open, none created today, and the last one not left to lapse). A plan waiting for the person holds back picked rows and playbooks. Its deadline is the next day's same hour, it expires rather than counts as missed, it is announced after the coalescing window, and it does not use up the day's off-cycle run; an off-cycle run earlier the same day takes its place. A plan answering it is an addendum. Three requests in a row never started stop it, as they stop off-cycle requests. `get_due.today` (optional, null without an X connection or a recent reply) is zooi's brief: `date`, `x_handle`, `read_at`, `followers`, `followers_change`, `replies` (`posted` today, `queued`), `posts` (`hours`, `views`, `kinds` with `count`, `views` and `average`, `best`, `worst`; their `text` is external), `problems` (`reply_missing`, `x_read_failed`) and `note`. Unknown is null, never 0. `report_run_request`'s `outcome` takes an optional `note` of up to 600 characters on what to change tomorrow; a number that is not in the brief is refused (`run_request_note_number_ungrounded`, path `outcome.note`). `GET /api/products/{id}/brief` returns the same brief to the person's web app.

**Bet is now campaign (2026-10-18, plan M6 step 6c).** zooi says campaign where it said bet, as a new tool name and new fields: `draft_campaign_reading` with `campaign_id`; `get_due.campaigns`, `campaigns_due` and `campaign_id` in `readings_due` and `work_orders`; `campaigns`, `campaign_ref` and `campaign_id` in `propose_plan`; the `campaign_reading` candidate in `get_playbook`; and refusal codes such as `campaign_inactive`. Until 2026-12-31 the old names keep working for plugins 0.1.13 and older: `draft_bet_reading` with `bet_id`, `get_due.bets`, `bets_due` and `bet_id`, and a plan sent with `bets`, `bet_ref` and `bet_id`. Refusals use the new codes only.

**Playbook format v2 (2026-10-23, plan M8 step 8b).** `get_playbook` returns `zooi.playbook/2`: the fields of `/1` plus `inputs`, `requires`, `triggers`, `cooldown_days` and each step's `deliverable`; its skill text has one section per step. `get_due.playbooks` adds `ready` and `missing`; a plan action adds the optional `inputs`; a pull request order adds `inputs` and `playbook_acceptance`. The additions are optional, but the checks are new: a plan that follows a playbook with required inputs and leaves them out, or follows one the product is not ready for, is refused with a reason code the agent can act on. Plugin 0.1.16's `plan` and `do` skills read them.

**Campaign tables (2026-10-24, plan M8 step 8d).** A person can add units to an active campaign's table (links or paths that fit a playbook's unit patterns), pick candidate rows for the next plan, or set them aside with a reason, which cools their unit down for the playbook's `cooldown_days`; all three need a person's session and have no MCP tool. `get_due` adds the optional `picked_units`; a plan action takes one up with its `opportunity_id`, and approval converts the row like any candidate. Units a person added are not discussions: they are left out of `candidates` and `judge_candidates`. Plugin 0.1.17's `plan` skill reads them.

**The first implementation's read tools are gone (2026-10-24).** `get_plan` returned the first implementation's daily work queue and decisions, and `get_diagnosis` its saved rule-based assessment; neither was the agent's plan, no skill called them, and their data stopped changing when the heartbeat no longer schedules that implementation's triage and diagnoses (design/plan.md §2). A plan is read with `get_due` (`pending_plan`, `recent_plans`) and submitted with `propose_plan`. Calls to the old names fail as unknown tools.

**Hosted pages are retired (2026-10-19, plan M6 step 6e).** zooi no longer hosts early-access pages or keeps signup lists (docs/product-decisions.md 2026-10-18): `propose_page` and `get_due.early_access` are gone. A product's own signup page sends its signups as events ([events.md](events.md)); the `signup-page` playbook describes the work. Old public addresses (`/launch/<key>`) lead to the product's website or say the page moved.

### Person-requested playbooks

A `run_requests` item with `kind: "playbook"` carries `playbook: { id, version, inputs }`. The person started it in the web app; it is intent, not approval. Read `get_playbook`, preserve the selected inputs, and submit a separate addendum with this `run_request_id`. Only actions following that playbook are accepted. For `weekly-review`, draft only matured readings instead. Report the start and outcome as usual. These requests neither coalesce with automatic triggers nor consume the automatic off-cycle allowance.
